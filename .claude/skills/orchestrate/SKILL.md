## Роль

Ты (главная сессия) — оркестратор. Сам код в этой фазе ты не пишешь: ты планируешь, порождаешь воркеров, собираешь и мержишь. Исключение — малые дифы по critical-находкам ревью и разрешение конфликтов мержа.

## Цикл

1. **Декомпозиция.** Разбей аргументы на независимые задачи. Если две задачи трогают одни и те же файлы (проверь поиском по коду: Grep/Glob) — объедини их в одну либо поставь в последовательную цепочку: параллельные ветки с пересечением дадут конфликт на мерже. Гарантированные конфликты в этом репо:
   - schema-изменения (drizzle-миграции делят journal/snapshot в `drizzle/`) — только цепочкой;
   - правки шипнутых скиллов (генерируемая копия в `plugins/openseo/skills` обновляется `pnpm sync-plugin-skills`);
   - новые зависимости (конфликт `pnpm-lock.yaml`);
   - версионный bump плагина — воркеры его НЕ делают; если смерженный набор добавляет MCP-инструмент или меняет шипнутый скилл, сделай один bump сам при мерже (правила — AGENTS.md).

2. **Спавн.** По одному агенту `task-worker` на задачу, одним сообщением (параллельно), каждому `isolation: "worktree"`. В промпте воркеру — полная самодостаточная постановка: что сделать, где в коде смотреть, критерий готовности, slug ветки. Воркер не видит этот чат.
   - База worktree по умолчанию — `origin/main`; если локальный main впереди origin/main, сначала запушь или скажи об этом пользователю.
   - Воркер сам переименует ветку в `feat/<slug>` / `fix/<slug>` / `refactor/<slug>` / `docs/<slug>`; актуальное имя бери из его отчёта, при сомнении — `git worktree list`.
   - Кап: максимум 3 воркера одновременно (каждый делает `pnpm install` в своём worktree).
   - Зависимые задачи: спавни следующую после завершения предыдущей, передавай в промпт «ветка X уже смержена / содержит Y».

3. **Сбор.** Дождись уведомлений о завершении. Упавший/зависший воркер — перезапусти с уточнённым промптом; повторный провал — сделай задачу сам в основном чекауте обычным образом.

4. **Ревью.** Как только ОДИН воркер завершился (не дожидаясь остальных) — породи `branch-reviewer`, передав путь к его worktree и имя ветки. Ревью ветки A идёт параллельно работе воркера B.
   - Рецензент вернёт вердикт `clean` / `minor` / `critical` + список находок.
   - `critical`: ветка не мержится. Исправь находки сам малым дифом прямо в worktree воркера (`git -C <worktree> ...`, `pnpm lint:fix`, коммит `Fix: review findings`); большой фикс — верни задачу в очередь как новую задачу для task-worker.

5. **Отчёт.** Таблица: задача → ветка → статус → проверено → находки ревью. Покажи пользователю до мержа.

6. **Мерж.** Только после подтверждения пользователя (или сразу, если он явно попросил в исходном запросе):
   - В основном чекауте, по одной ветке за раз: `git merge --no-ff <branch>` (или ff, если ветка одна). Конфликты разреши сам, сохранив смысл обеих сторон; сомневаешься — спроси.
   - После каждого мержа: `git worktree remove <path>` и `git branch -d <branch>`.
   - В конце: `pnpm ci:check` на main как smoke-проверку (это локальная замена CI) и при необходимости — единственный bump версии плагина.
   - Не пушь без явной просьбы.

## Правила

- Воркеры коммитят сами (их протокол — `.claude/agents/task-worker.md`); ты не коммитишь за них. Рецензент код не меняет; правки по critical-находкам делаешь ты.
- Никаких PR/пуша/инфраструктуры из оркестратора без явной просьбы.
- Если задача одна — оркестрация не нужна, работай сам в обычном режиме.
